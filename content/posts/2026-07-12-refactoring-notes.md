《重构》这本书有个副作用：第一次读它的人，往往会变成「代码洁癖」。

我就是这样。2019 年读完，接下来的半年里，我热衷于把同事的代码改成书上推荐的样子，并为此引发过不止一次争论。

这次重读，感觉完全不一样了。不是书变了，是我终于能读懂那些**没有被加粗**的句子。

## 一、重构的前提是测试

书的第一章就在讲这个，但当年我直接跳过去看「坏味道」清单了。

Martin Fowler 说得很明确：

> 重构是在不改变代码可观察行为的前提下，改善其内部结构。

关键词是**可观察行为**。如果没有测试，你怎么知道行为没变？

当年我的做法是：改完，跑一下，页面上点一点，看起来正常，提交。现在回头看，这不是重构，这是**带着侥幸心理的改写**。

有了测试之后，重构的性质完全变了：

- 从「小心翼翼、改一处检查一处」，变成「放心大胆地连续改造，跑测试就行」
- 从「一次改一大块」，变成「小步快跑，每步都能验证」
- 从「需要跟人争论这样改对不对」，变成「测试通过就是对的」

**没有测试的重构不是重构，是赌博。**

## 二、重构和性能优化是两件事

书里有一节专门讲这个，我当年完全没读懂。

Fowler 的观点是：**先重构，让代码结构清晰，然后再做性能优化。** 反过来的顺序是错的。

原因很实际。性能优化通常会牺牲可读性——加缓存、内联展开、手工管理内存。如果代码本身还是一团乱麻，你根本不知道瓶颈在哪，优化也无从下手。

更关键的是，**优化完之后你往往需要再重构一次**。因为优化引入的那些技巧（缓存层、批处理、预计算），会让原本清晰的结构变得难懂。这时候需要重新把边界理清楚。

所以完整的循环是：

```text
重构 → 让结构清晰 → 找出瓶颈 → 优化 → 再重构 → 结构重新清晰
```

跳过第一步直接优化，等于在迷雾里找路。

## 三、什么时候不该重构

这是我这次重读收获最大的一节。

Fowler 列了几种情况，其中两种我当年完全无法接受：

**第一，代码太烂，不如重写。**

当一段代码的结构已经烂到「重构的每一步都要先修好十个别的问题」，重写反而更划算。

判断标准不是主观的"感觉好烂"，而是：

- 加一个小功能，需要改动超过五个文件
- 每修复一个 bug，就引入一个新 bug
- 没有人能说清楚这段代码的完整行为

**第二，临上线前不要重构。**

重构会产生大量改动，改动会产生风险。在需要稳定的时候引入风险，是把技术洁癖凌驾于业务之上。

这一条我当年最不服气。现在明白了：**技术债的偿还时机，本身也是技术判断的一部分。**

## 四、坏味道清单的正确用法

书里那 24 种坏味道，我当年是当 checklist 用的——逐条对照，看到就改。

现在我的用法变了：**它们是线索，不是判决书。**

举几个例子。

**「过长函数」**——书里给的建议是抽成小函数。但我在实际项目里遇到过：一个 200 行的函数，是一段线性执行的初始化流程，每一步都依赖前一步的结果，抽成小函数反而让数据流变得难以追踪。

这时候更好的做法可能是**用注释把段落分隔开**：

```js
function initApplication() {
  // ---- 1. 加载配置 ----
  // ...

  // ---- 2. 建立数据库连接 ----
  // ...

  // ---- 3. 注册中间件 ----
  // ...
}
```

**「重复代码」**——也不是看到就抽。两段看起来一样的代码，如果**变化的原因不同**，就应该保持分开。强行合并之后，任何一边的需求变化都会牵扯到另一边。

判断标准是：**它们是因为同一个原因而重复，还是碰巧长得像？**

**「注释」**——书里说注释是坏味道，因为「需要注释说明的代码说明代码本身不清晰」。这句话有前提：注释在解释**代码做了什么**。

但注释在解释**为什么这么做**的时候，是不可替代的：

```js
// 这里必须用 <= 而不是 <，因为上游的 offset 是闭区间（历史原因，
// 见 2023-04 的分页 bug 修复记录）。改成 < 会导致最后一页少一条。
for (let i = start; i <= end; i += 1) { /* ... */ }
```

这种注释不是坏味道，是**给未来的人的警示牌**。

## 五、重构的节奏

书里提到了「两顶帽子」的比喻，当年我读过就忘了。

意思是：写代码的时候，你头上要么戴着「添加功能」的帽子，要么戴着「重构」的帽子，**同一时间只能戴一顶**。

戴着添加功能的帽子时，就不要顺手改结构。戴着重构的帽子时，就不要顺便加新逻辑。

这个纪律听起来很教条，但非常有用。因为两者混在一起的时候，一旦出问题，你无法判断是**新逻辑有 bug** 还是**重构改坏了原有行为**。

我现在会显式地在提交信息里标注：

```text
refactor: 把订单状态判断抽成策略对象（行为不变）
feat: 支持部分退款
```

分开提交，分开 review，分开回滚。这是**让问题可以被定位**的最便宜的办法。

## 最后

《重构》最容易被误读的一点是：它看起来像一本技术手册，实际上是一本**关于决策的书**。

它教的不是「怎么把代码改成某个样子」，而是「在什么情况下、以什么节奏、改到什么程度就停手」。

六年前我读到的是一堆规则，现在读到的是**规则的边界**。

> 知道什么时候不用某个手段，比知道这个手段怎么用更难。前者需要经验，后者只需要阅读。
